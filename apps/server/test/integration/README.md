# Тесты против настоящей базы

Тонкий слой поверх обычных тестов: шесть сценариев, проходящих путь целиком,
с настоящим Postgres, настоящими миграциями, настоящей очередью и настоящим
Chromium. Prisma здесь не подменяется нигде — это условие, а не пожелание.

## Зачем

28 августа 2026 массовый выпуск падал пятисотой на любом запуске. Ошибка
лежала на `main` с блока 9: `pg_advisory_xact_lock` возвращает `void`,
а `$queryRaw` такой столбец разобрать не умеет — P2010. Ядро продукта
не работало вовсе.

979 тестов при этом были зелёными. Не поймали потому, что двойник Prisma
в `generation.test-utils.ts` подменял ровно тот метод, где жила ошибка:
тест проверял двойника, а не базу. Нашёл человек, вручную нажав кнопку.

Зелёные тесты означали «код не противоречит сам себе», а не «оно работает».
Этот слой добавляет второе. Старые тесты он не заменяет: они по-прежнему
полезны там, где проверяют чистую логику — склонение ФИО, разбор таблиц,
сборку письма.

## Как запускать

```bash
pnpm test:integration
```

Нужны Postgres и Redis. Локально их поднимает `docker-compose.dev.yml`
из корня репозитория; по умолчанию тесты идут на `localhost:5432`
и в пятнадцатую базу Redis на `localhost:6379`. Другие адреса:

```bash
INTEGRATION_DATABASE_URL=postgresql://gramota:gramota@localhost:55433/gramota \
INTEGRATION_REDIS_URL=redis://localhost:63791/0 \
pnpm test:integration
```

Обычный `pnpm test` базы не требует и не запускает этот каталог —
за это отвечает `exclude` в `apps/server/vitest.config.ts`. Иначе
`pnpm test` перестал бы работать на машине без поднятой базы,
и им перестали бы пользоваться.

В конвейере слой идёт отдельной обязательной работой `integration`
(`.github/workflows/ci.yml`) с сервисами `postgres` и `redis`.

## Как устроено

- **Своя схема на прогон.** `global-setup.ts` заводит схему `it_<случайное>`,
  накатывает в неё `prisma migrate deploy` с нуля и в конце сносит целиком.
  Разъехавшийся порядок миграций падает здесь, а не на выкате.
  Пятнадцатая база Redis перед прогоном очищается — часть прошлого прогона
  дошла бы до воркера этого.
- **Пустая база на файл.** `resetDatabase` вычищает таблицы перед каждым
  файлом: список таблиц спрашивается у самой базы, а не перечисляется руками.
- **Службы собраны руками** (`support/app.ts`). Через `Test.createTestingModule`
  не выходит: контейнер Nest читает типы конструкторов из `design:paramtypes`,
  а эту разметку кладёт `tsc`; Vitest собирает через esbuild, который её
  не умеет вовсе. Связи от этого не спрятаны, а наоборот видны целиком
  в одном файле.
- **Один процесс, один файл за раз.** Файлы делят схему, очередь и браузер.

## Что подменено — и только это

1. **Объектное хранилище** — `support/storage.ts`, карта в памяти.
   S3 в конвейере нет, а поднимать MinIO ради байтов значит платить
   минутами за то, что проверяет `s3-key.test.ts`. Байты при этом
   настоящие: тест рендера достаёт из хранилища тот самый PDF,
   который напечатал Chromium, и заглядывает внутрь.
2. **Страница печати** — `support/render-page.ts`. `PdfRenderer` открывает
   браузером `<RENDER_BASE_URL>/render?token=…`, то есть страницу кабинета;
   собирать её в конвейере — это React, шрифты и минуты работы, ничего
   не говорящей о базе. Заменена только сама страница: подписанный токен,
   `RenderController` с настоящей Prisma, подстановка переменных
   из `@gramota/shared` (включая падежи), Chromium и `page.pdf()` —
   всё настоящее.
3. **Почтовый воркер не поднят.** Его `enqueue` без `onModuleInit` ничего
   не делает: письмо остаётся в базе, на SMTP никто не ходит. Проверяется
   решение «слать или не слать», а не почтовый шлюз.

Prisma не подменяется ни в одном месте.

## Как проверить, что тесты не бесполезны

Тест, который не падает на настоящей поломке, не нужен. Проверяется так:

```bash
# в apps/server/src/generation/generation.service.ts заменить
#   await tx.$executeRaw`SELECT pg_advisory_xact_lock(${key}::bigint)`;
# на  $queryRaw — и запустить слой
pnpm test:integration
```

Должно упасть с `P2010: Failed to deserialize column of type 'void'`.
