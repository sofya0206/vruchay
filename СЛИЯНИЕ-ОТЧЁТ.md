Сборочная ветка **`pravki-posle-testa`**, создана от `main` (`841a0de`).
В `main` ничего не слито, в прод ничего не выкатывалось.

Порядок слияния — как задано: **C → B → A**.

| Ветка | Коммит | Как слилась |
|---|---|---|
| C — сервер и данные (`claude/c-server-data-tasks-531132`) | `cd5c7c5` | перемоткой, 40 файлов |
| B — почта (`claude/pochta-zadachi-pravki-e45910`) | `d721576` | без конфликтов, 7 файлов |

## Главное: конфликтов не было ни одного — и это не значит, что всё срослось

Git не остановился ни разу. Две поломки он при этом склеил молча, обе — в паре
B×C, обе найдены руками при чтении результата слияния, а не по красному тесту.
Исправлены отдельным коммитом `1687965`, между слиянием B и слиянием A.

### 1. Новый код B читал окружение мимо схемы настроек

`apps/server/src/mail/mail.service.ts`

C перевела весь файл с `process.env` на `ConfigService` — в том числе завела
геттер `publicUrl`, который прогоняет адрес через `baseUrl()`. B в тот же файл
добавила новый метод `unsubscribeLink()` для заголовка `List-Unsubscribe`,
и он читал `process.env.PUBLIC_URL` напрямую: в базе B этого геттера ещё
не существовало.

Строки разные, поэтому конфликта не было. Формально «оба намерения сохранились»,
по существу — намерение C нарушено: в файле, который весь переведён на схему,
осталось одно сырое чтение окружения.

**Решено:** `unsubscribeLink()` берёт `this.publicUrl`. Заодно чинится и то,
чего в ветке B не было видно: `baseUrl()` снимает косую черту на конце адреса,
сырое чтение её не снимало — при `PUBLIC_URL` с чертой ссылка отписки
в заголовке получалась вида `…ru//api/v1/u/…`.

### 2. Тесты B создавали службы старым числом аргументов

`apps/server/src/mail/send-one.test.ts`, `apps/server/src/mailing/mailing.service.test.ts`

C добавила четвёртым аргументом конструктора `ConfigService` и в `MailService`,
и в `MailingService`. Оба файла тестов B — новые, git внёс их как есть,
а в них `new MailService(prisma, storage, smtp)` и
`new MailingService(prisma, mail, processor)`.

**Решено:** четвёртым аргументом передан `testConfig()` из
`apps/server/src/config/env.test-utils.ts` — тот самый помощник, который C
завела ровно для этого случая.

Отдельно: блок «заголовок отписки» в `send-one.test.ts` подменял
`process.env.PUBLIC_URL` и восстанавливал его в `afterEach`. После перевода
на `ConfigService` эта подмена ни на что не влияет — тест проверял бы не то,
что думает. Блок переписан на значение из `testConfig` (`https://vruchay.ru`),
`afterEach` и возня с окружением убраны.

# Доделано после слияния

Два пункта, которые ветки оставили друг другу, закрыты в этой же сборочной
ветке — коммиты `501d829` и `524df7d`.

## Предел бесплатной пробы через ConfigService (`501d829`)

`apps/server/src/generation/generation.service.ts` читал
`process.env.FREE_DOCUMENT_LIMIT` напрямую — последнее такое чтение в службах.
C завела настройку в схеме (`config/env.ts:102`) и перевела на `ConfigService`
всё, до чего дотянулась, но генерация была зоной A, а A про эту строку
не вспомнила.

Разница не косметическая: схема проверяет, что значение — целое положительное,
а `Number(process.env…)` при мусоре в переменной даёт `NaN`, и тогда сравнение
`used + adding > limit` ложно всегда — предел не срабатывает вовсе.

Попутно: заглушка настроек в `free-limit.test.ts` отвечала `3` на любой ключ
и после перевода вернула бы предел 3 вместо 50. Заменена на `testConfig`
из той же схемы, что и боевой запуск. В `generation.test-utils.ts` ключ добавлен
рядом с `ORG_ACTIVE_JOBS`, тем же способом, — `queue-order.test.ts` не тронут.

Прямых чтений окружения в `apps/server/src` не осталось нигде, кроме точек
входа (`main.ts`, `worker.ts`, `cli.ts`), где окружение и есть источник.

## Частичный уникальный индекс на письма (`524df7d`)

Миграция `20260829130000_emails_one_live_per_stream`:

```sql
CREATE UNIQUE INDEX "emails_document_to_kind_live"
  ON "emails" ("document_id", lower("to_email"), "kind")
  WHERE "status" IN ('queued','sent','delivered','opened') AND "to_email" <> '';
```

### Два отступления от задания B — оба вынужденные

**`to_email <> ''` — иначе индекс ломает ночную уборку от ветки C.**
Это не предположение, а воспроизведённый отказ. На чистой базе с индексом
ровно по спецификации B:

```
=== два письма разным людям по одному материалу — вставлены
=== теперь ночная уборка сроков хранения стирает адреса:
ERROR:  duplicate key value violates unique constraint "emails_naive"
DETAIL:  Key (document_id, to_email, kind)=(…, , transactional) already exists.
```

Уборка от C стирает адрес участника через год, оставляя статус доставки
(`retention.service.ts:134`, `ANONYMIZED_ADDRESS = ''`). Два доставленных
письма разным людям по одному материалу превращаются в две одинаковые строки
`(материал, '', поток)`, и `updateMany` падает — каждую ночь. Ни одна ветка
этого увидеть не могла: B не знала про обезличивание, C не знала про индекс.
Обезличенному письму отправлять всё равно некуда — по той же причине его
пропускает и `NOT: { toEmail: '' }`, который C добавила в `resendFailed`.

**`lower(to_email)` — иначе «Ivanov@…» обходит защиту.** Так же сделан
соседний частичный индекс `tilda_requests_one_per_email` из миграции
`20260802163000`; он же и прецедент того, что частичные индексы в этом проекте
пишутся сырым SQL — Prisma их в схеме не описывает и при сверке не замечает
(`migrate diff` по-прежнему отвечает «No difference detected»).

### Правка кода: транзакция заменена на вставку с пропуском дублей

`createEmails` и `resendFailed` собирали письма через
`$transaction([...create])`. С индексом такая транзакция откатывалась бы
целиком: из-за одного повторного адреса не ушло бы ни одного письма, включая
те, что были в списке впервые. Обе переведены на `createManyAndReturn`
со `skipDuplicates` — это `ON CONFLICT DO NOTHING`: повтор молча выпадает,
остальные уходят, а `queued` в ответе становится честным счётом.

### Дубли, накопленные до миграции

Индекс не встанет поверх данных, которые ему противоречат. Миграция сначала
удаляет повторы, оставляя самое раннее письмо группы, и печатает их число
(`RAISE NOTICE`). Проверено на засеянной базе:

```
NOTICE:  Повторных писем удалено: 1
```

— удалён поздний дубль `Ivanov@Example.RU` (пойман через `lower`), ранний
`ivanov@example.ru` остался, а пара `sidorov` `failed` + `queued` уцелела
целиком: недоставленное лежит вне индекса, и законная переотправка
не пострадала. В рабочей базе владельца дублей нет вовсе — проверено
запросом на чтение, 20 писем, ноль групп.

### Проверки

**Обычные, идут в `pnpm -r test`** — `mailing.service.test.ts`, четыре новых.
Заглушка Prisma теперь повторяет условие индекса, иначе проверка гонки
проверяла бы сама себя. Окно гонки воспроизводится честно: создание писем
вызывается дважды по одному плану, то есть по журналу, прочитанному до первой
записи. Через `send()` это бессмысленно — второй вызов упёрся бы в прежнюю
проверку в коде и про индекс не сказал бы ничего.

Падают до правки, проходят после — проверено откатом `createEmails` к прежнему
виду: **3 из 4 красные**. Четвёртая — «повторная отправка недоставленного
по-прежнему работает» — сторож в другую сторону: если подменить условие
на обычный уникальный индекс, краснеет она и ещё один тест ветки B.
Оба предупреждения B, таким образом, теперь под тестом.

**Против настоящей базы** — новый `live-email-index.db.test.ts`, шесть проверок,
под флагом по образцу `CHROMIUM_TESTS`:

```bash
DB_TESTS=1 DATABASE_URL=postgresql://… pnpm --filter @gramota/server test
```

Без базы пропускается, `pnpm -r test` остаётся зелёным везде. Он и проверяет
то, чего заглушка не может: само условие в SQL. Прогнан на одноразовой базе
с накатанными миграциями — 6 зелёных. Что он ловит:

| Состояние индекса | Итог |
|---|---|
| индекса нет | 3 красных |
| индекс ровно по спецификации B | 2 красных (регистр и ночная уборка) |
| индекс из миграции | 6 зелёных |

Флаг описан в `README.md` рядом с `CHROMIUM_TESTS`.
