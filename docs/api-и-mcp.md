# API и вопрос про MCP-сервер

Сделано 07.08.2026.

## Короткий ответ: API достаточно, MCP пока не нужен

Вопрос был — делать ли MCP-сервер, чтобы сервисом могли управлять
помощники на основе ИИ, или хватит API. Ответ: **сейчас хватит API, и его
надо было делать в любом случае**. Причины по убыванию веса.

**1. MCP — это обёртка поверх API, а не замена ему.** Что бы мы ни строили
для ИИ, оно будет ходить в те же самые маршруты. Сделав API с токенами, мы
получили фундамент и для MCP, и для интеграции с чужой программой
федерации, и для выгрузки из СпортОрг. Начинать с MCP значило бы строить
крышу раньше стен.

**2. Наши пользователи не настроят MCP-сервер.** Локальный MCP требует
установить программу, прописать путь в конфигурационный файл клиента
и перезапустить его. Секретарь федерации, ради которого мы упрощаем каждую
кнопку, этого не сделает — и правильно, что не сделает. Удалённый MCP
(по HTTP, без установки) снял бы это возражение, но он требует OAuth,
которого у нас нет и который сам по себе больше работы, чем весь MCP.

**3. Спроса пока нет.** Ни один разговор с федерациями не начинался
со слов «а можно я буду управлять этим из Клода». Строить под воображаемого
пользователя — самый дорогой способ ошибиться.

**Когда делать MCP:** когда появится хотя бы один человек, который просит.
Это примерно двести строк поверх готовых маршрутов — обёртка, объявляющая
инструменты «создать материал», «загрузить список», «выпустить»,
«разослать». Отдельного хранилища и отдельных прав ей не понадобится.

## Что сделано

`Authorization: Bearer vru_…` принимается везде, где принимается вход
человеком. Это не отдельное API «для роботов»: маршруты те же самые,
и правила доступа к чужим материалам от способа входа не зависят.

### Токен

Выдаётся в кабинете: «Настройки» → «Доступ для программ». Раздел свёрнут
по умолчанию — он нужен единицам, а объяснять «токен доступа» тому, кто
пришёл выпустить грамоты, незачем.

- Показывается **один раз** при выдаче. В базе лежит sha256, не сам токен:
  список токенов в кабинете — первое, что прочтёт получивший доступ
  к чужой открытой вкладке, и там не должно быть ничего рабочего.
- Приставка `vru_` — чтобы сервисы поиска утечек (GitHub и подобные)
  узнавали наш секрет в чужом репозитории и предупреждали.
- Не больше десяти действующих на организацию.
- Отзыв помечает запись, а не удаляет её: нужно уметь ответить,
  кто и когда завёл этот доступ.

### Права

| В кабинете | Что может |
|---|---|
| «Выпускать документы» | материалы, получатели, выпуск, рассылка |
| «Полный доступ» | то же плюс удаление материалов |

**Управлять людьми токен не может никогда** — ни пригласить сотрудника,
ни поменять права, ни сменить пароль, ни выдать новый токен. Это не
настройка, а свойство: иначе токен, выданный «чтобы бот выпускал грамоты»,
становится способом завести себе человеческий доступ в обход владельца,
а утёкший токен — способом отобрать организацию. Токен, умеющий выдавать
токены, вдобавок нельзя отозвать: он тут же выдаст себе следующий.

Проверено: приглашение сотрудника, просмотр состава и выдача токена
по токену отвечают 403 с объяснением; удаление материала правами
«выпускать» — 403; отозванный, обрезанный и чужой токен — 401.

### Что записывается в журнал

Выдача и отзыв токена — с именем того, кто это сделал. Действия самого
токена подписываются в журнале как «Токен «название»», так что видно,
что именно сделала программа, а не человек.

## Пример

```bash
# Список материалов
curl https://vruchay.ru/api/documents \
  -H "Authorization: Bearer vru_ВАШ_ТОКЕН"

# Новый материал
curl -X POST https://vruchay.ru/api/documents \
  -H "Authorization: Bearer vru_ВАШ_ТОКЕН" \
  -H "content-type: application/json" \
  -d '{"title":"Грамота участника"}'

# Строка получателя
curl -X POST https://vruchay.ru/api/documents/{id}/recipients/rows \
  -H "Authorization: Bearer vru_ВАШ_ТОКЕН" \
  -H "content-type: application/json" \
  -d '{"data":{"name":"Иванов Пётр Ильич","email":"petr@example.ru"}}'

# Выпуск
curl -X POST https://vruchay.ru/api/documents/{id}/generate \
  -H "Authorization: Bearer vru_ВАШ_ТОКЕН" \
  -H "content-type: application/json" \
  -d '{"format":"pdf"}'

# Рассылка
curl -X POST https://vruchay.ru/api/mail/send/{id} \
  -H "Authorization: Bearer vru_ВАШ_ТОКЕН"
```

## Что осталось по этой части

- **Описание маршрутов для сторонних разработчиков.** Сейчас их
  единственное описание — исходный код. Для подрядчика федерации нужна
  страница со списком: адрес, поля, ответ. OpenAPI-схема снимала бы этот
  вопрос и заодно давала бы готовый набор инструментов для будущего MCP.
- **Отдельное ограничение частоты для токенов.** Сейчас действуют общие;
  выгрузка тысячи документов в них упереться не должна, но проверять это
  на боевом сервере не хочется.
