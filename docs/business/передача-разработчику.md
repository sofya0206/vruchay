# Передать проект разработчику — по шагам

Два действия: код через GitHub, ключи отдельно. Порядок важен —
сперва убедиться, что в репозитории нет секретов, и только потом
публиковать.

---

## Шаг 1. Завести закрытый репозиторий

Откройте https://github.com/new и заполните:

| Поле | Что выбрать |
|---|---|
| Repository name | `vruchay` |
| Visibility | **Private** — обязательно |
| Add a README / .gitignore / license | **ничего не отмечать** |

**Почему обязательно Private.** В репозитории лежат не только исходники:
там расчёт себестоимости, шаблоны договоров, модель угроз и описание
устройства защиты. Открытый репозиторий отдаёт это конкурентам,
а описание защиты — тем, кто будет её обходить.

Последние три галочки не отмечать: у нас уже 62 коммита, и созданные
GitHub файлы помешают первой отправке.

## Шаг 2. Отправить код

GitHub покажет адрес репозитория. Подставьте своё имя пользователя:

```bash
cd "/Volumes/T7 Shield/Проект вручай /gramota" && git remote add origin https://github.com/ВАШ-ЛОГИН/vruchay.git && git branch -M main && git push -u origin main
```

Спросит логин и пароль — вместо пароля нужен **токен**: GitHub давно
не принимает обычный пароль. Создать: https://github.com/settings/tokens
→ «Generate new token (classic)» → отметить только `repo` → скопировать
и вставить вместо пароля.

## Шаг 3. Дать разработчику доступ

Settings → Collaborators → Add people → его имя на GitHub.

## Шаг 4. Передать ключи — **не через GitHub**

В репозитории ключей нет и быть не должно: git не забывает. Удалив файл
следующим коммитом, вы не уберёте его из истории — только добавите ещё
один коммит. А это доступ к базе, хранилищу, рассылке и резервным копиям
системы с персональными данными детей.

**Чем передать.** Годится любой способ, где содержимое не остаётся
навсегда в чужой системе:

- общий сейф в менеджере паролей (Bitwarden, 1Password, «Пассворк») —
  лучший вариант: видно, кто и когда смотрел, доступ отзывается;
- зашифрованный архив, пароль к нему — отдельным каналом (голосом,
  в другом мессенджере).

**Чего не делать:** не отправлять `.env` письмом, в общий чат, в issue
на GitHub и не класть в репозиторий «временно».

### Что именно передать

Возьмите файл с сервера:

```bash
ssh -i ~/.ssh/vruchay root@178.72.160.214 'cat /opt/vruchay/.env' > vruchay.env
```

В нём 35 заполненных значений. Самые чувствительные:

| Ключ | К чему даёт доступ |
|---|---|
| `POSTGRES_PASSWORD`, `DATABASE_URL` | вся база: участники, адреса, документы |
| `SESSION_SECRET` | подделка сессии любого пользователя |
| `SMTP_PASSWORD` | рассылка от имени вашего домена |
| `MAIL_WEBHOOK_SECRET` | подмена состояний писем в реестре |
| `SELLER_*` | банковские реквизиты в счетах |
| `OPERATOR_EMAIL`, `OPERATOR_PHONE` | контакты оператора ПДн из политики |

Отдельно от `.env`:

- **ключ SSH** `~/.ssh/vruchay` — доступ к серверу целиком;
- **ключ расшифровки резервных копий** (`age`) — он на сервере не хранится
  нарочно, лежит у вас в менеджере паролей;
- доступы к панели Selectel и кабинету DashaMail.

### Лучше, чем отдавать свои ключи

Где можно — заведите разработчику **собственные** доступы, а не делитесь
своими:

- свой ключ SSH: он присылает вам `.pub`, вы дописываете его
  в `/root/.ssh/authorized_keys` на сервере;
- своя учётная запись в панели Selectel;
- свой пользователь в кабинете «Вручая» (Настройки → Кто работает
  в организации).

Так вы увидите в журналах, кто что сделал, и сможете закрыть доступ
одному человеку, не меняя ключи всем.

## Шаг 5. Что сказать разработчику

Первым делом пусть прочитает [ПЕРЕДАЧА.md](../../ПЕРЕДАЧА.md) в корне
репозитория: там как поднять у себя за полчаса, из чего всё собрано,
какие три решения менять нельзя и почему, и что не доделано.

Отдельно предупредите про две вещи, на которых легко обжечься:

1. **Перед выкладкой прогонять `./scripts/prod-dry-run.sh`.** Боевая
   конфигурация отличается от рабочей, и 07.08.2026 выкладка положила
   сервис на четверть часа из-за настройки, которая ломается только
   в бою. Проверка на своей машине ловит это за пять минут.

2. **Новый подрядчик, который увидит данные участников, требует
   договора-поручения** по ч. 3 ст. 6 152-ФЗ — до подключения, а не
   после. Это касается и его самого, если он будет работать с боевой
   базой.
