# Модель угроз

Составлена 01.08.2026 по методике STRIDE, применённой к фактической архитектуре,
а не к абстрактному веб-приложению. Пересматривается при добавлении публичных
точек входа: интеграции с Тильдой, виджетов, страницы проверки подлинности.

Требование уровня защищённости для наших данных — **УЗ-3/УЗ-4**: обрабатываются
ФИО, адрес электронной почты, телефон, организация и спортивный результат;
специальных категорий и биометрии нет ([ADR-0003](adr/0003-jurisdiction-rf-rb.md)).

## Что защищаем и кто пострадает

| Актив | Почему ценен | Кто пострадает при утечке |
|---|---|---|
| Персональные данные участников | Тысячи ФИО и адресов, среди них дети 12–15 лет | Участники и их родители; федерация как оператор — штраф и предписание |
| Право отправлять письма с домена клиента | Позволяет писать от имени федерации | Получатели фишинга; репутация домена федерации |
| Выданные сертификаты и страница проверки | Подделка обесценивает награды | Федерация: подложные дипломы с «подтверждением» |
| Учётные данные и сессии | Полный доступ к данным организации | Все клиенты |
| Инфраструктурные секреты | Доступ к базе, хранилищу, почте | Все клиенты сразу |
| Доступность в день награждения | Награждение нельзя перенести | Клиент теряет мероприятие, мы — клиента |

## Границы доверия

```
Интернет
   │
   ├─► Caddy ──► SPA (статика)              граница 1: аноним → приложение
   │      └───► API  ──── сессия в cookie   граница 2: аноним → данные организации
   │
   ├─► Публичные точки входа без сессии     граница 3: САМАЯ ОПАСНАЯ
   │      • /render?token=…  (страница печати)
   │      • формы Тильды, виджеты   — Фаза 4
   │      • /verify/<id>            — Фаза 6
   │
   └─► CI → реестр образов → сервер          граница 4: цепочка поставок

Внутри периметра: PostgreSQL, Redis, S3, Chromium воркера
Наружу уходит: письма с вложениями → почтовый провайдер (ПДн покидают периметр)
```

Ключевое наблюдение: **почти все реальные находки пришлись на границу 3** —
там, где нет сессии и авторизация держится на чём-то ещё.

награждение нельзя перенести на завтра.

| Угроза | Состояние |
|---|---|
| Chromium исчерпывает память и роняет базу | ✅ **исправлено 01.08.2026.** Воркер вынесен в отдельный контейнер с `mem_limit: 2g` и `shm_size: 512m`; при превышении ядро убьёт воркер, а не базу, и `restart` вернёт его в строй |
| Наплыв заявок с публичных форм | ⏳ Фаза 4: суточные лимиты на интеграцию и лимит по адресу |

## Что делать, в порядке приоритета

1. **Журнал согласий** — до первой формы на Тильде. Без него мы не сможем доказать
   наличие согласия, а по договору обязаны предоставить эти сведения оператору.
2. **Шифрование резервных копий** до первого дампа с боевыми данными.
4. **Закрепить действия GitHub по хешу** вместо тега.
5. **Заменить `--no-sandbox` профилем seccomp** при переезде на прод.
6. **Ограничение частоты в Redis** — перед вторым экземпляром приложения.
7. **Записи в `audit_log`** — вместе с приглашением пользователей.

## Чего сознательно не делаем

**Двухфакторная аутентификация** — пока пользователей единицы и все свои.
Обязательна к моменту, когда появятся приглашения внешних участников.

**Аттестация системы защиты** — для УЗ-3/УЗ-4 избыточна. Инфраструктура Selectel
уже аттестована ФСТЭК, этого достаточно, пока клиент не потребует иного.

**Выделенный IP для почты** — 2 100 ₽/мес при наших объёмах не окупается;
на общем IP провайдера доставляемость выше, чем на непрогретом своём.

**Шифрование данных в базе** — защищает от кражи диска, но не от компрометации
приложения, а именно она вероятнее. В политике обработки данных это заявлено
честно: шифруется передача, не хранение.
