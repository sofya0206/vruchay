# Сквозная проверка формы на сайте

Автотестами не покрывается по той же причине, что и генерация: нужны браузер,
Redis, S3, почтовый шлюз и запрос с чужого источника. Прогоняется руками перед
релизом и после любой правки публичной части (`apps/server/src/tilda/`).

Ключевая особенность этой части: **все запросы межсайтовые**. Скрипт живёт на
сайте клиента, а обращается к нам. Проверка с той же машины и того же порта
ничего не доказывает — половина возможных поломок (политика ресурса,
предварительный запрос OPTIONS) там просто не проявляется.

## Подготовка

Локальный `.env` лежит в `apps/server/.env` и смотрит на контейнеры
из `docker-compose.dev.yml`. **Не копировать сюда `.env` из корня**: там
боевые ключи, и тестовые грамоты уехали бы в рабочее хранилище, а письма —
настоящей почтой.

В `apps/server/.env` обязательно `RENDER_BASE_URL=http://localhost:5173`
(или порт, на котором запущен веб): страницу печати отдаёт веб-приложение,
и без этого Chromium ждёт её на адресе из `PUBLIC_URL`, где ничего нет.
Симптом — заявка падает с `page.waitForFunction: Timeout`.

```bash
docker compose -f docker-compose.dev.yml up -d
pnpm --filter @gramota/server exec prisma migrate deploy
pnpm --filter @gramota/server build && node apps/server/dist/main.js
pnpm --filter @gramota/web dev
```

Бакет в MinIO сам не создаётся:

```bash
docker run --rm --network host --entrypoint sh minio/mc:latest -c \
  "mc alias set local http://localhost:9000 gramota gramota-secret && mc mb --ignore-existing local/gramota"
```

В кабинете: подключить домен отправки и создать отправителя (локально домен
подтверждается прямой правкой `mail_domains.status`, в DNS фиктивных доменов
записей нет), затем создать интеграцию, указав в разрешённых сайтах `localhost`.

Страница с формой поднимается на другом порту — тогда источник будет чужим:

```bash
python3 -m http.server 8080
```

В HEAD страницы вставляются две строки из карточки интеграции. В форме нужны
поля `doc_id` (скрытое), `name`, `email`, чекбокс `consent` и поле-ловушка
`website`, скрытое стилями.

## Что проверяем

1. **Скрипт подключился.** Если браузер пишет про `Cross-Origin-Resource-Policy`
   — значит на публичном пути потерялся заголовок `cross-origin`.
2. **Отправка формы.** Появляется окно, приходит письмо с кодом в теме.
   Ошибка про CORS на этом шаге означает, что не отвечает предварительный
   запрос OPTIONS.
3. **Ввод кода** → окно «Готовим документ» → «Готово» со ссылкой на скачивание.
4. **Файл**: `pdftotext -enc UTF-8` показывает имя участника; `pdffonts` —
   встроенный шрифт, а не подставленный системный.
5. **Письмо участнику** с вложением (Mailpit на `localhost:8025`).
6. **Журнал заявок** в карточке интеграции: строка со статусом «выдан».
7. **Согласия**: в таблице `consents` две записи на заявку — `certificate`
   и `marketing` — с версией текста, адресом обращения и сайтом формы.

## Приём формы прямо на адрес (без скрипта)

Второй способ подключения: адрес `/api/v1/tilda-create` вписан в Тильде
в «Свой скрипт для приёма данных». Проверяется отдельно, потому что путь
другой — без нашего скрипта на странице.

```bash
curl -X POST http://localhost:3000/api/v1/tilda-create \
  -H 'Origin: http://localhost:8080' \
  --data-urlencode "secure=<токен>" --data-urlencode "doc_id=<документ>" \
  --data-urlencode "mask_name=Кузьмина-Караваева Анна" \
  --data-urlencode "mask_email=anna@example.ru" \
  --data-urlencode "consent=Согласна" --data-urlencode "COOKIES=tmr_lvid=abc"
```

1. Ответ — **200**, не 201: Тильда считает отправку удавшейся только по двухсотому.
2. В режиме «код на почту» приходит письмо **со ссылкой**, а не с кодом:
   окно для кода рисует скрипт, которого на странице нет. Переход по ссылке
   показывает страницу «Адрес подтверждён», заявка уходит в обработку.
3. Служебные поля Тильды (`tranid`, `formid`, `COOKIES`) в `fields` заявки
   не попадают — проверить в журнале заявок.
4. Без подтверждения и без сверки со списком (`authMode: none`,
   `checkList: false`) прямая отправка **отклоняется**: источник в таком
   запросе проверить нельзя, а токен виден в разметке страницы.
5. `doc_id=all` — отказ с подсказкой подключить скрипт.

### Проверено на настоящей Тильде (22.08.2026)

Сайт sca-swimming.com, скрытая страница с pop-up формой BF502, сервер
на маке через `cloudflared tunnel` (при сломанном DNS помогает
`GODEBUG=netdns=cgo`). Что выяснилось:

- Webhook подключается в **Настройки сайта → Формы → Webhook**, потом
  включается галочкой у формы в «Подключенные сервисы». Без галочки
  Тильда показывает «Спасибо», но никуда не шлёт.
- При подключении Тильда шлёт проверочный `test=test` и принимает адрес
  только по ответу 200 — маршрут отвечает `{ok:true}`.
- Отправка **серверная**: запрос приходит с IP Тильды (65.21.49.40),
  без заголовка источника, но с User-Agent посетителя. Поэтому лимит
  по адресу на `tilda-create` поднят: все сайты Тильды делят один IP.
- Тильда прикладывает поля `tildaspec-*` (cookie, formid, fp…) —
  с дефисом, разбор их отбрасывает; в заявку попало только `name`.
- Pop-up форма по ссылке `#popup:myform` не открывается — только кликом
  по кнопке на странице или `t702_showPopup('<id блока>')` из консоли.
- Полный круг: форма → ссылка в письме → подтверждение → PDF → письмо
  с вложением. Пройден.

## «Мои документы»

Блок `<div data-vruchay-my></div>` или форма с `doc_id=all`. Код на почту
спрашивается всегда, независимо от режима интеграции.

1. Ввод почты → письмо с кодом → перечень выданных документов с датами.
2. Скачивание из перечня работает и для документов старше часа — окно
   здесь не по времени выдачи, а по сеансу (час после кода).
3. Перечень без кода (`GET /api/v1/tilda/my/<listId>` до подтверждения) —
   «Список не подтверждён».
4. Чужой адрес, не получавший документов, — пустой перечень, а не ошибка:
   факт «документов нет» раскрывать безопасно, факт «есть» — только по коду.

## Отказы, которые обязаны срабатывать

| Что делаем | Ожидаемое поведение |
|---|---|
| Заявка с источника `evil-<домен клиента>` | отказ, в журнале сервера — причина |
| Заполнено скрытое поле `website` | ответ как при успехе, заявка не создаётся |
| Снята галочка согласия | отказ на проверке полей |
| Чужой `documentId`, не входящий в интеграцию | обобщённый отказ |
| Шесть неверных кодов подряд | после пятого заявка переходит в «отклонена» |
| Повторная заявка на тот же адрес | `already_issued`, новый файл не создаётся |
| Ссылка на скачивание через час | «Срок действия ссылки истёк» |
| Адрес не из реестра при включённой сверке | «Этого адреса нет в списке участников» |
| Заявка без `ma_email` при «только из кабинета» | «Войдите в личный кабинет» |
| Правка одного переключателя интеграции | остальные настройки не сбрасываются |

## Что уже проверено (22.08.2026)

Полный путь через `tilda-create` на локальном стенде: заявка с чужого
источника → код → генерация → письмо с вложением → скачивание. Сверка
со списком, приём только из кабинета и все отказы из таблицы — отработали.

оставляет значения по умолчанию); второй разборщик форм валил сервер
на старте.
