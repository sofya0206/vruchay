# Слой интеграционных тестов против настоящей базы

## Зачем это делается

28.08.2026 массовый выпуск падал пятисоткой на любом запуске. Баг лежал на `main` с блока 9: `pg_advisory_xact_lock` возвращает `void`, а `$queryRaw` такой столбец разобрать не умеет — P2010. Ядро продукта не работало вовсе.

979 тестов были зелёными. Не поймали, потому что двойник в `generation.test-utils.ts` подменял ровно тот метод Prisma, где жила ошибка: тест проверял двойника, а не базу. Нашёл человек, вручную нажав кнопку.

Вывод, который надо закрыть кодом: **зелёные тесты сегодня означают «код не противоречит сам себе», а не «оно работает».** Ни один тест в репозитории не разговаривает с настоящим Postgres.

Задача — добавить тонкий слой, который разговаривает. Не переписывать существующие тесты, не гнаться за покрытием: шесть-восемь сценариев, проходящих путь целиком.

## Как работать

Выполни всё до конца самостоятельно, вопросов не задавай. Ветка `integration-tests` от `main`, в конце — pull request, PR не мержить. В прод ничего не выкатывать: правило CLAUDE.md — только после того, как я явно напишу слово «выкатывай».

## Что уже есть

- `vitest run` в `apps/server`, конфига нет — всё на умолчаниях
- `docker-compose.dev.yml` поднимает `postgres:16-alpine`, `redis:7-alpine`, MinIO и почтовую заглушку
- Миграции Prisma накатываются `prisma migrate deploy`, есть `prisma/seed.ts`
- Рендер PDF — настоящий headless Chromium через Playwright, он уже в зависимостях
- CI (`.github/workflows/ci.yml`) — одна работа `check`: lint, prisma generate, playwright install, build, тесты

## Что делать

**А. Отдельный прогон, не смешанный с обычным.** Заведи скрипт `test:integration` и отдельный конфиг vitest. Обычный `pnpm test` должен остаться быстрым и не требовать базы — иначе им перестанут пользоваться.

**Б. Настоящая база, никаких двойников.** Тесты этого слоя подключаются к живому Postgres, миграции накатываются с нуля перед прогоном. Каждый прогон работает в своей схеме или своей базе и убирает её за собой, чтобы тесты не наследовали данные друг друга. Prisma здесь не мокается **ни в одном месте** — это условие задачи, а не пожелание.

**В. Сценарии. Шесть-восемь, не больше:**

1. Импорт таблицы получателей → проверка строк → массовый выпуск: задание доходит до конца, файлы созданы, `verify` по `publicId` их находит. Это ровно тот путь, который сегодня падал.
2. Замок на организацию: два одновременных выпуска в одной организации не ломают друг друга. Именно здесь жил P2010 — тест должен падать, если кто-нибудь вернёт `$queryRaw`.
3. Чужое — 404, а не 403: документ, файл, строка реестра из другой организации. Проверить на настоящих запросах Prisma со скоупом по `orgId`, а не на моках.
4. Транзакционное письмо нельзя отправить рекламным потоком и наоборот — на настоящих записях `EmailTemplate` и `Email` с полем `kind`.
5. Перевыпуск: старый документ получает состояние «заменён», новый на него ссылается, страница проверки старого честно говорит о замене. Отзыв — отдельное состояние.
6. Реестр отдаёт страницу за разумное время на объёме в несколько тысяч строк — выдача постраничная, не выгрузка всего в память.

Если по ходу окажется, что какой-то сценарий требует переписывать боевой код — не переписывай, опиши в PR.

**Г. Рендер.** Хотя бы один тест должен получить настоящий PDF от Chromium и проверить, что в нём есть подставленные значения — фамилия в нужном падеже. Без этого «выпуск прошёл» ничего не значит: файл может быть пустым.

**Д. CI.** Добавь в `ci.yml` отдельную работу `integration` с сервисами `postgres` и `redis` (обычные `services:` GitHub Actions, не docker compose). Она должна быть обязательной для PR, а не запускаться руками. Если прогон выходит дольше пяти минут — скажи в PR, будем думать, что вынести.

## Не трогай

Существующие тесты и двойники не переписывай и не удаляй — они полезны там, где проверяют чистую логику (склонение ФИО, разбор таблиц, сборка письма). Задача — добавить слой, а не заменить старый.

## Приёмка

- `pnpm test` работает без запущенной базы, как раньше.
- `pnpm test:integration` поднимает миграции с нуля и проходит на чистой базе.
- Если вернуть `$queryRaw` вместо `$executeRaw` в `withOrgLock` — интеграционный прогон падает. **Проверь это на самом деле: сломай, убедись, что упало, верни обратно.** Тест, который не падает на настоящей поломке, бесполезен.
- В CI появилась работа `integration`, она зелёная на PR.
- Ни один тест этого слоя не мокает Prisma.
