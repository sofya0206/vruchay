# Правила работы над проектом

## Архитектура

Монорепозиторий pnpm (`pnpm-workspace.yaml`): `apps/*` + `packages/*`,
зависимости рабочего пространства внедряются (`injectWorkspacePackages: true`),
Fastify закреплён одной версией на всё дерево (`pnpm-workspace.yaml` → `overrides`).

- **`packages/shared`** (`@gramota/shared`) — контракт между редактором, превью
  и серверным рендером: схема макета листа (`src/schema/layout.ts`, версия —
  `schemaVersion`), правила наград и разрядов (`src/awards/`), склонение ФИО
  и транслитерация (`petrovich`), измерение текста по метрикам шрифтов
  (`src/fonts/measure.ts` — то, что второй Chromium-тест в README сверяет
  с реальным браузером), Zod-схемы валидации. Собирается в CJS и ESM
  (`tsconfig.cjs.json` / `tsconfig.esm.json`) — `pnpm --filter @gramota/shared build`
  нужно перед тем, как сервер или веб увидят изменения (в dev `pnpm dev`
  собирает всё параллельно, но после `git pull`/переключения веток может
  понадобиться ручная пересборка).
- **`apps/server`** (`@gramota/server`) — NestJS 11 на Fastify-адаптере
  (`src/main.ts`), Prisma + PostgreSQL, BullMQ + Redis, Playwright для рендера
  PDF. Модули в `src/*` по предметной области (`documents`, `recipients`,
  `awards`, `generation`, `render`, `mailing`, `verify`, `registry`, `tilda`,
  `payments`, `org`, `team`, …), собраны в `src/app.module.ts`. Генерация PDF —
  очередь: `generation/generation.processor.ts` (воркер BullMQ) вызывает
  `generation/pdf-renderer.ts`, который печатает лист в Playwright/Chromium
  по одноразовому подписанному токену (`render/render-token.ts` →
  `render/render.controller.ts`, отдельный `RenderModule` — то, что открывает
  Chromium, а не браузер посетителя). Авторизация — сессии Fastify
  (`@fastify/secure-session`) плюс guard'ы в `auth/` (`auth.guard.ts` —
  залогинен, `roles.guard.ts` — роль в организации, `platform-only.guard.ts`,
  `humans-only.guard.ts`); принадлежность объекта организации проверяется
  в каждом сервисе по `orgId` из `current-user.decorator.ts`, а не по телу
  запроса (см. правило BOLA/IDOR выше). Публичные маршруты (Тильда, проверка
  по QR) — под rate-limit из `common/throttle.guard.ts`.
- **`apps/web`** (`@gramota/web`) — React 19 + Vite + Tailwind 4. Структура
  `src/*` зеркалит серверные предметные области (`documents`, `recipients`,
  `awards`, `verify`, `registry`, `billing`, …) плюс `editor/` (редактор
  макета листа на контракте из `packages/shared`, `editor/rich` — Tiptap для
  текстовых полей), `shell/` (каркас кабинета, навигация), `landing/` и
  `public/` (посадочная и публичные страницы вне кабинета), `render/` —
  страница, которую по токену печатает серверный Playwright. Сборка —
  `tsc --noEmit` → `vite build` → `prerender.mjs` (пререндер посадочной для
  SEO); PWA — `vite-plugin-pwa`.
- **Инфраструктура для разработки** — `docker-compose.dev.yml`: `postgres`,
  `redis`, `minio` (S3-совместимое хранилище), `mailpit` (почтовый шлюз для
  писем). Прод — `docker-compose.prod.yml`, миграции там отдельная разовая
  служба перед стартом приложения и воркера.

## Основные команды

```bash
pnpm install                                        # из корня, один раз
pnpm dev                                             # server:3000 + web:5173 параллельно
pnpm --filter @gramota/server test                   # тесты одного пакета (vitest run)
pnpm --filter @gramota/server test <путь-или-имя>     # один файл/тест — обычные флаги vitest
pnpm --filter @gramota/server exec prisma migrate dev # новая миграция после правки schema.prisma
pnpm lint && pnpm -r test && pnpm -r build            # перед коммитом (см. ниже — обязательно nest build)
```

Остальные команды — Chromium-тесты, тесты против настоящей базы, интеграционные
сценарии, порядок «локально → выкат» — описаны ниже в разделах «Тесты против
настоящей базы» и «Порядок работы».

## Безопасность — Secure by Design (обязательно, без исключений)

Действует при создании функций, исправлении багов и рефакторинге. Перед применением правки —
быстрый анализ рисков для этой фичи. Если задача нарушает OWASP Top 10 — сначала предупредить
владельца, потом писать код.

1. **Валидация входящих данных** — строго на бэкенде, по принципу whitelist: проверка типов,
   длины, допустимых значений. В проекте для этого Zod-схемы; DTO без схемы не принимаются.
2. **Защита от инъекций** — только параметризованные запросы. В проекте это Prisma; при
   необходимости сырого SQL — только `$queryRaw` с тегированным шаблоном, никогда не
   `$queryRawUnsafe` со склейкой строк.
3. **Контроль доступа (BOLA/IDOR)** — при любой операции с объектом по идентификатору
   проверять принадлежность объекта организации текущего пользователя. Каждый запрос к
   `documents`, `sheets`, `files`, `recipient_rows` фильтруется по `orgId` из сессии,
   а не по значению из тела запроса. Отсутствие прав возвращает 404, а не 403 — чтобы
   не подтверждать существование чужого объекта.
4. **Секреты** — только переменные окружения. `.env` в `.gitignore`, в репозитории лежит
   `.env.example` с плейсхолдерами. Никаких ключей, токенов и паролей в коде, тестах,
   миграциях и документации.
5. **Вывод данных** — экранирование пользовательского ввода на фронтенде. React экранирует
   по умолчанию; `dangerouslySetInnerHTML` запрещён без явной санитизации. HTML тела писем
   и макеты сертификатов санитизируются перед рендером в Chromium.
6. **Ошибки** — полный текст и стек логируем на сервере, клиенту отдаём обобщённое сообщение
   без путей, SQL и стека. В проде `NODE_ENV=production` отключает подробные ответы Nest.

Дополнительно для этого проекта: публичные эндпоинты (Тильда, виджеты, верификация) всегда
под rate-limit; персональные данные не попадают в логи и в события мониторинга.

## Перед началом любой задачи — свериться с main (обязательно)

Над проектом одновременно работает несколько сессий по разным тз. Уже был случай, когда
две сессии за день написали одно и то же (12 интерфейсных правок и транслитерацию ФИО),
потому что стартовали от устаревшего локального `main`: к моменту старта то же самое
уже было слито через PR. Работа ушла в мусор, ветки закрыли как дубли.

Поэтому **первое действие в любой новой ветке — до чтения кода и до первой правки**:

```
git fetch origin
git log --oneline -30 origin/main
git status -sb                     # ветка должна быть от свежего origin/main
```

Дальше — проверить, не сделано ли уже то, что просит тз:

1. Прогнать по `origin/main` поиск по ключевым словам задачи (имена файлов, функций,
   переменных из тз): `git log --oneline -40 origin/main`, `git grep -l "<ключевое слово>" origin/main`.
2. Посмотреть открытые и недавно закрытые PR: `gh pr list --state all --limit 20`.
3. Посмотреть чужие ветки: `git branch -r` — особенно `origin/claude/*`, это работа других сессий.

**Если находится, что задача уже сделана — не писать код.** Остановиться и написать об этом
в ответе: где именно лежит готовое (PR, ветка, файлы) и что осталось незакрытым, если осталось.
Считать задачу выполненной чужой работой — нормальный и правильный исход, а не провал.

Ветку всегда брать от свежего `origin/main`, а не от локального `main` и не от соседней ветки.

## Выкат

Прод описан в [docker-compose.prod.yml](docker-compose.prod.yml): миграции —
отдельная разовая служба, приложение и воркер стартуют только после её успеха.
План первого запуска — [docs/launch-day.md](docs/launch-day.md).

Образ собирается через `pnpm deploy`, поэтому зависимости рабочего пространства
внедряются (`injectWorkspacePackages` в pnpm-workspace.yaml), а `prisma` лежит
в рабочих зависимостях — без неё в образе нечем применить миграции.

## Тесты против настоящей базы

`pnpm test` остаётся быстрым и базы не требует. Рядом живёт отдельный слой —
`pnpm test:integration`: шесть сценариев проходят путь целиком на настоящем
Postgres, с миграциями с нуля, настоящей очередью и настоящим Chromium.
Prisma в нём не подменяется нигде. Нужен для правок в выпуске, замке
на организацию, правах по `orgId`, потоках писем, перевыпуске и реестре;
подробности и разбор подмен — в `apps/server/test/integration/README.md`.

Локально ему хватает `docker-compose.dev.yml`. В конвейере это отдельная
обязательная работа `integration`.

## Ручные проверки

Две части системы автотестами не покрываются намеренно — им нужны браузер,
очередь, хранилище и почтовый шлюз:

- [генерация PDF](docs/e2e-generation.md) — после правок рендера, шрифтов, вёрстки листа;
- [форма на сайте](docs/e2e-tilda.md) — после правок публичной части `src/tilda/`.
  Проверять обязательно с чужого источника: на своём порту межсайтовые
  ограничения не проявляются.

## Порядок работы: сначала локально, на сервер — только с разрешения

**Правило.** Любая правка проверяется на машине владельца. На боевой сервер
она уезжает **только после его явного подтверждения**, отдельным действием.

Причина не в осторожности, а в опыте: сборка образов шла на самом сервере,
каждая оставляла 3,2 ГБ мёртвых слоёв, и за день диск заполнился целиком.
Первой упала база — PostgreSQL не смог записать контрольную точку, ушёл
в бесконечное восстановление, и сервис отвечал пятисотой ошибкой на вход.
Владелец не мог войти в собственный сервис из-за того, что мы выкатывали
непроверенные правки по одной.

### Как проверять локально

Тяжёлый образ на 3,2 ГБ нужен только боевому серверу. Локально приложение
запускается напрямую, а инфраструктуре хватает лёгких образов:

```bash
docker compose -f docker-compose.dev.yml up -d     # база, Redis, хранилище, почта
pnpm --filter @gramota/server dev                  # сервер
pnpm --filter @gramota/web dev                     # кабинет на localhost:5173
```

Серверу нужен **свой** `apps/server/.env` — корневой `.env` предназначен для
docker compose, и Nest его не читает. Заведите его из `.env.example`, иначе
сервер поднимется без базы и хранилища.

Когда закончили — погасите инфраструктуру, иначе контейнеры висят до
перезагрузки:

```bash
docker compose -f docker-compose.dev.yml down
```

Перед показом владельцу — обязательно:

```bash
pnpm -r test
pnpm --filter @gramota/server exec nest build      # именно nest build, а не только tsc:
pnpm --filter @gramota/web build                   # он воспроизводит сборку в Docker
```

`tsc --noEmit` недостаточно: он однажды прошёл на устаревшем клиенте Prisma,
а сборка в Docker упала — там клиент генерируется заново.

### Когда выкатывать

Только после слов владельца «выкатывай». Не «посмотри», не «сделай»,
а именно подтверждение выката. Одна сборка на несколько проверенных правок,
а не сборка на каждую.
