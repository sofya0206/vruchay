# RUNBOOK — эксплуатация сервиса

Единственный источник правды об инфраструктуре. Обновляется при каждом изменении.

## Окружения

| Окружение | Где | Как деплоится |
|---|---|---|
| dev | локальный Mac (colima + docker compose dev) | `pnpm dev` |
| staging | VPS (куплен? — см. чек-лист ниже) | GitHub Actions `Deploy staging` после CI на main |
| prod | VPS | вручную запуском workflow (после появления) |

## Среда разработки на Mac

Проект и виртуальная машина colima лежат на внешнем диске **T7 Shield**:

- репозиторий — `/Volumes/T7 Shield/Проект вручай /gramota`;
- данные colima — `/Volumes/T7 Shield/Проект вручай /colima`, а `~/.colima`
  это символическая ссылка на них.

Так вышло не из любви к внешним дискам: внутренний диск Mac заполнен
(197 из 228 ГБ), а один только прод-образ сервера весит 3,3 ГБ.

Отсюда одно правило: **диск должен быть подключён до запуска colima**.
Если отключить его при работающей машине, для неё это выглядит как
выдернутый из компьютера диск. Порядок работы простой: подключили диск —
`colima start` — работаете; закончили — `colima stop` — отключаете.

Откат, если внутренний диск освободится: `colima stop`, убрать ссылку
`~/.colima`, перенести папку обратно.

## DNS-записи домена

Заводятся в панели Selectel: DNS → Доменные зоны → `vruchay.ru.`
Порядок важен — часть записей появляется только после того, как известен адрес сервера.

| Когда | Тип | Имя | Значение | Зачем |
|---|---|---|---|---|
| После создания прод-сервера | A | `@` | IP прод-сервера | Сайт открывается по адресу |
| Тогда же | A | `www` | IP прод-сервера | Привычный адрес с www |
| Тогда же | A | `staging` | IP стейджинга | Отдельный контур для проверок |
| Перед Фазой 3 (почта) | TXT | `@` | `v=spf1 include:… ~all` | Разрешает нашему шлюзу слать письма от домена |
| Тогда же | TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:postmaster@vruchay.ru` | Отчёты о письмах, не прошедших проверку. Начинаем с `p=none` и ужесточаем, когда убедимся, что своё проходит |
| Тогда же | TXT | `_vruchay-verify` | токен из карточки домена в сервисе | Подтверждение владения доменом отправки |
| Выдаст почтовый провайдер | TXT | `<селектор>._domainkey` | ключ DKIM | Подпись писем |

⚠️ TLS-сертификат выпускает Caddy сам, как только A-запись начнёт указывать
на сервер и порт 80 будет доступен. Отдельно ничего заказывать не нужно.

## Первичная настройка VPS (staging и prod одинаково)

```bash
# на сервере (Ubuntu 24.04):
curl -fsSL https://get.docker.com | sh
mkdir -p /opt/gramota && cd /opt/gramota
# скопировать docker-compose.prod.yml и заполнить .env (см. .env.example + прод-секреты)
docker login ghcr.io -u <github-user> -p <PAT с read:packages>
docker compose -f docker-compose.prod.yml up -d
```

## Деплой

**Перед выкатом, если менялся `docker-compose.prod.yml`:**

```bash
./scripts/prod-dry-run.sh
```

Он поднимает боевую конфигурацию целиком на своей машине — с теми же
образами, ограничениями и проверками здоровья — и убирает всё за собой.
Это единственное место, где боевой compose исполняется до сервера:
в разработке работает `docker-compose.dev.yml`, и настройки вроде
`cap_drop`, `mem_limit` и `security_opt` там не проверяются никогда.

**Так уже уронили бой 07.08.2026.** В боевой compose добавили
`cap_drop: [ALL]` всем службам сразу. Официальные образы postgres и redis
стартуют от root: выправляют права каталога данных и только потом
переходят к своему пользователю. Без `CHOWN` и `SETUID` они пишут
«Operation not permitted», не проходят проверку здоровья и тянут за собой
всё остальное — сервис лёг целиком примерно на четверть часа. Пробный
прогон поймал бы это за минуту.

Нашим собственным образам (api, worker) возможности ядра не нужны:
в Dockerfile стоит `USER app`, они ничего не переприсваивают. Caddy нужен
`NET_BIND_SERVICE` — занять порты 80 и 443.

**Ловушка при пересборке.** `docker compose build web` на этом файле
**молча ничего не делает**: у служб нет секции `build`, образы собирает
`scripts/server-deploy.sh` прямой командой с аргументами из `.env`.
Команда завершается с кодом 0 и пустым выводом, а образ остаётся прежним —
легко решить, что пересобрал, и выкатить старое. Пересобирать только
скриптом выката.

## Резервные копии

Скрипты: [`scripts/backup.sh`](scripts/backup.sh) и
[`scripts/restore-drill.sh`](scripts/restore-drill.sh).

Дамп шифруется **до** выгрузки в хранилище, ключом age. На сервере лежит только
публичная половина ключа: тот, кто получит доступ к серверу, сможет сделать новую
копию, но не прочитать ни одну из прежних. Секретный ключ хранится вне сервера —
у владельца, в менеджере паролей. **Потеря секретного ключа = потеря всех копий.**

Подготовка перед первым боевым запуском:

- [ ] `age-keygen -o vruchay-backup-key.txt` на своей машине, не на сервере
- [ ] публичную строку (`age1…`) положить в `/etc/vruchay-backup.env` как
      `BACKUP_AGE_RECIPIENT`, секретный файл — в менеджер паролей и никуда больше
- [ ] на сервере: `apt-get install -y age postgresql-client awscli`
- [ ] бакет `vruchay-backups` с отдельным ключом доступа (только запись и чтение
      своего префикса — не тот же ключ, что у боевого бакета с файлами)
- [ ] crontab: `0 3 * * * . /etc/vruchay-backup.env && /opt/vruchay/scripts/backup.sh >> /var/log/vruchay-backup.log 2>&1`
- [ ] через сутки проверить, что копия появилась и весит правдоподобно

Учебное восстановление — раз в квартал, на staging, с записью даты сюда:

| Дата | Копия | Итог |
|---|---|---|
| — | — | ещё не проводилось |

Проверено локально: `pg_dump --no-owner --clean --if-exists` разворачивается в
пустую базу без единой ошибки, все таблицы на месте. Шифрование и выгрузка в S3
непроверены — на машине разработки нет ни `age`, ни `aws`; проверяются первым же
прогоном на сервере.

(добавится при первом прод-деплое). Локально: `pnpm --filter @gramota/server prisma:migrate`.

## Инциденты

1. Сервис лежит → `docker compose ps`, `docker compose logs api --tail 100`.
2. Очередь зависла → Bull Board (появится в Фазе 2), рестарт worker:
   `docker compose restart worker` — задания в Redis переживают рестарт.
3. Письма не уходят → статус DashaMail, лимиты тарифа, `docker compose logs api | grep mail`.
